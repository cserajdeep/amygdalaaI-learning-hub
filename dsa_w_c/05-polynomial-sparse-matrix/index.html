Polynomial Representation Using Arrays
A polynomial P(x) = a₀ + a₁x + a₂x² + ... + aₙxⁿ can be stored as a simple array where the array index IS the exponent and the value at that index is the coefficient.
The Core Idea CONCEPT

Example: P(x) = 5 + 0x + 3x² + 0x³ + x⁴ is stored as:

// coeff[i] = coefficient of x^i int coeff[5] = {5, 0, 3, 0, 1}; // degree = size - 1 = 4
coeff[] — index = exponent
✅ Pros: O(1) access to any term's coefficient by exponent; simple addition/subtraction (just add index-wise).
⚠️ Cons: Wastes space for sparse polynomials — e.g. x¹⁰⁰⁰ + 1 needs an array of 1001 slots to store just 2 non-zero terms. (That's exactly why the sparse/triplet technique later in this module exists!)

How Each Operation Works REFERENCE
Addition — O(max(m,n))
Pad the shorter array with zeros, then C[i] = A[i] + B[i] for every index i.
Subtraction — O(max(m,n))
Same idea: C[i] = A[i] − B[i] for every index i.
Multiplication — O(m×n)
Every term of A multiplies every term of B; exponents add. C[i+j] += A[i] × B[j] for all i, j — this is a convolution.
Sparse Matrix → Triplet Representation
A sparse matrix has mostly zero elements. Storing every cell wastes memory — instead we store only the non-zero ones as (row, col, value) triplets.
Why Triplets? CONCEPT
A dense N×N matrix always uses N² cells of memory, even if 95% are zero.

The triplet (3-tuple) form stores a header (rows, cols, nonZeroCount) followed by one row per non-zero element: (row, col, value). If a matrix is sparse enough, this uses far less memory than the dense grid.

Why Match on A.col == B.row? CONCEPT
Standard matrix multiplication rule: C[i][k] = Σⱼ A[i][j] × B[j][k].
A non-zero A[i][j] can only contribute to the result if there's a matching non-zero B[j][k] — i.e. B's row equals A's column j. This is why the algorithm scans A's triplets, and for each one, scans B's triplets looking for B.row == A.col, instead of touching every cell of a dense grid.
